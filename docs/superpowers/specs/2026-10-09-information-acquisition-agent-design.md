# 信息获取 Agent 与工具归属重构设计

状态：待用户书面审阅；尚未修改产品代码。

项目：当前独立仓库 `trip-evidence-agent`，基线 `2dfb62d`。
本仓库没有初始化 OpenSpec。本次沿用现有 `docs/superpowers/specs/` 文档结构，不创建 OpenSpec 目录。

## 1. 目标与已确认需求

用户已在聊天中确认：事项收集能力并入信息获取 Agent；火车、酒店、攻略改成其内部工具；信息获取负责选择工具、检查结果、补查与综合总结；后续规划读取结构化条件与分领域候选结果。偏好更新应在本轮查询前生效。

本次交付是 V0 命令行项目的架构和接口重构，保持现有模型配置、来源契约、预算计算、记忆与执行记录能力。酒店和攻略未配置数据接口时继续明确返回 unavailable，不用演示数据替代真实数据。

顶层仍是中心化编排的业务工作流。信息获取有自己的工具循环；不另建总结 Agent，不将意图识别改造成通用自主主 Agent。

## 2. 方案选择

考虑过三种方案：继续独立调度四个节点；由信息获取嵌套调用事项收集子 Agent；将条件提取并入信息获取，三个查询节点转为工具。

采用第三种。独立事项收集与工具参数生成存在重叠，现有三个查询类没有模型调用。合并职责可以保持结构化数据，又避免额外固定模型调用和重复的顶层能力入口。

## 3. 顶层节点与依赖

| 节点 | 默认阶段 | 职责 |
| --- | --- | --- |
| IntentionAgent | 调度前 | 意图、query 改写、任务安排 |
| OrchestrationAgent | 全程 | 执行依赖、并发、上下文和结果传递 |
| PreferenceAgent | 1 | 长期偏好变更提取 |
| MemoryQueryAgent | 1 | 相关历史信息查询 |
| RAGKnowledgeAgent | 1 | 内部制度与差旅标准检索问答 |
| InformationQueryAgent | 2 | 条件整理、查询工具循环、结果总结 |
| ItineraryPlanningAgent | 3 | 依据候选和约束组合行程 |

数字越小越早，同批次只并行无依赖任务。实际依赖优先：需要本轮新偏好的节点必须在偏好处理之后；需要某个检索结果的任务在该检索之后执行。阶段编号不要求每轮全部存在。

调度时去重顶层节点，确保已请求的信息获取在规划之前。查询请求不隐式追加规划。政策、记忆和偏好请求按需独立执行。规划无需外部补查且已有完整资料时可以只调度规划。

删除 event_collection、train_search、hotel_search、travel_guide 的顶层注册和自动插入规则；它们的能力不得再次作为全局 Skill 摘要暴露成可调度 Agent。

## 4. 输入、上下文与偏好

入口将用户原文 original_query 作为程序确定的数据保留，不能依赖模型重新生成原文。rewritten_query 来自意图识别，供任务理解使用。

信息获取接收两种 query、当前日期、相关会话资料、任务要求、effective_preferences 和相关前序结果。顶层描述其支持火车、酒店、攻略、天气与网页；具体工具 schema 只传给信息获取的模型调用。

成功的 PreferenceAgent 返回后，编排器按 append/replace 规则合并到本轮有效偏好，更新后续节点输入。无需先持久化再重新读取。重复反馈执行不能重复追加偏好。失败的提取结果不得覆盖有效偏好。

本次临时要求影响本轮查询，但不自动修改长期偏好。长期变更仍通过偏好提取和记忆保存流程完成。用户本轮明确要求优先于旧偏好。家庭住址不能自动成为本次出发地。

历史、政策检索结果是带来源的参考资料，不是新的系统指令。信息获取返回条件和查询事实，规划接收相关资料及完整需求；不把整个会话历史或内部运行日志无条件复制给每个模型调用。

## 5. 信息获取内部循环

继续使用 InformationQueryAgent 类名，显示名称更新为“信息获取”。保留现有模型配置并扩展模型交互；本地已安装的 AgentScope OpenAIChatModel 支持 tools/tool_choice 和 tool_use 响应。

流程：读取需求与有效偏好 → 模型整理条件并选择工具 → 程序校验参数 → 执行工具 → 将真实工具返回交回模型 → 判断补查、缺条件或结束 → 同一 Agent 总结。

使用模型工具调用协议，流式响应收齐后再执行完整调用；保留每个调用 ID 与对应返回消息。未知工具、无效参数和不存在的候选引用不能触发未经定义的操作。并行调用结束后，所有成功与失败返回都进入后续模型上下文。

条件缺失时不得调用对应接口；返回明确的缺失字段和补充提示，并保留其他已取得结果。模型可以从原文与已确认资料理解日期、人数；程序继续校验日期、人数、入住区间等。

综合总结由信息获取自己的后续模型调用完成，不设置独立总结 Agent。结构化结果由程序组装；模型只选择已有候选 ID 并解释差异，不能重写供应商价格、库存、来源、查询时间等事实。

## 6. 查询工具与现有 Provider

内部工具：train_search、hotel_search、travel_guide、weather_query、web_search。前三者成为函数工具，不继承 AgentBase、不调用模型。天气和网页搜索也通过统一的工具执行入口使用，网页工具只返回检索资料，避免内部再独立调用一次摘要模型。

保留 TrainQuery、HotelQuery、GuideQuery、AgentDataResult、Source 和候选类型，复用 providers.py、juhe_train.py、价格精度及来源校验。拆解 agent_support.py 对旧 Msg/previous_results 的依赖，让查询入口直接接受明确参数。

火车要求起终点与日期；沿用未知乘车人数可默认一人的既有规则。酒店要求城市、入住/离店日期和入住人数；未知值不得默认为一人或直接套用出发/返程日期。攻略日期未知时只提供不依赖日期的可验证资料，不声称当天开放或天气事实。

JuheTrainProvider 继续使用用户已接通的站到站查询。接口没有 limit/page 参数，不模拟服务端分页。可以按文档支持的车次类型、可预订状态、出发时段缩小查询范围；日期仍限北京时间今天起的 15 个日历日。

## 7. 候选池、筛选和预算

保留本轮完整的经过校验的候选池；给模型和规划的候选视图有数量限制。火车候选粒度是车次与席别组合；筛选时避免默认用同一车次的多个席别占满整个候选列表。

建议默认：火车最终候选最多 5 个，酒店/房型报价最终候选最多 5 个，可配置。不足时返回实际数量，不生成候选补足。攻略事实按来源和相关性组织，不能按酒店条数机械截断开放与预约依据。

工具结果先按明确硬约束筛选，再按有效偏好排序。价格与预算比较使用 Decimal，并区别每晚、入住总价和全程预算。价格未知不能视为满足预算；部分报价不能宣称全程预算已核实。

模型可以要求查看同一查询的其他本地候选，使用本地 candidate_offset/候选窗口，不把该参数发给聚合 API。同参数请求复用本轮候选池；只有真实接口条件变化或明确刷新时重新请求。最终候选和模型可见窗口保留 ID 及来源，全量数据留在程序中，不把全量原始响应反复塞入提示词。

明确硬约束不能被自主放宽。没有预算内候选时可以继续在已有候选和支持的数据源中查找；无法满足时如实返回，等待用户决定是否调整预算、地点或其他要求。

## 8. 输出契约与规划输入

InformationQueryAgent 返回程序组装的统一对象：

| 字段 | 内容 |
| --- | --- |
| status | ok / partial / needs_input / unavailable / error |
| summary | 基于工具返回生成的综合摘要 |
| travel_conditions | 已整理的明确出行条件及本轮约束 |
| domain_results | train / hotel / guide / weather / web 的独立结果 |
| missing_fields | 待补充的必要条件 |

前三种领域结果保持 AgentDataResult 字段：query、items、missing_fields、source、fetched_at、message、status。天气、网页使用相同外层结果字段，其 items 是带来源的天气资料或搜索资料。

一个工具失败不能丢弃其他成功结果。全部不可用/错误、部分成功、缺条件分别保留明确状态；空结果不等于接口异常，也不能直接断言无票/无房。最终完成状态不只取决于模型自述，程序核对请求领域和返回状态。

缺少完成规划所必需的用户条件时暂停依赖规划，先提示补充；不能把 needs_input 当作正常成功。只有部分数据不可用时可输出标明待核实部分的方案，不把建议伪装成已确认事实。

规划输入包含原始/改写后的 query、有效偏好、travel_conditions、domain_results 及相关政策/历史结果。摘要只辅助理解，选定车次和酒店必须引用已有 ID。规划和事实保护读取统一对象，必要时由内部数据适配器复用现有 guard_itinerary，不将工具重新变成顶层 Agent。

界面展示综合摘要、候选及来源、缺失条件和部分失败。价格、库存和预算从结构化结果重建，不能以模型摘要替代事实来源。

## 9. 规划反馈循环

信息获取可在本地判断查询结果是否满足条件。规划还可能发现候选之间的时间或组合冲突，可返回结构化 feedback：status=needs_requery、reason、domains、constraints。

编排器将有效反馈交回信息获取，复用本轮查询池和成功结果，仅针对受影响的领域补查，然后再次规划。不得重跑意图识别、偏好更新和无关任务。反馈约束不得改动用户已确认的硬条件；需要用户改变条件时返回待确认提示。

进入反馈前由规划给出具体可执行需求，而不是一个泛化的“不满意”。没有新查询依据、缺少用户条件或达到限制时结束并说明原因。需要补查的中间规划不保存为最终行程。

## 10. 循环、重试和执行记录

以下是需书面审阅的技术默认值，可配置：每次信息获取最多 6 次模型调用、10 次内部工具调用；每轮最多 1 次“规划 → 信息获取 → 再规划”的反馈。工具保留现有 30 秒超时边界。达到限制时保留已知结果，返回未完成原因，不继续循环。

反馈最多增加一次信息获取执行；同一轮最多两次信息获取、两次规划。本轮候选池和已执行请求记录跨反馈保留；不能通过再次进入信息获取清除缓存或绕过工具请求去重。模型是否支持工具调用应在实施测试中验证协议，真实服务支持情况不以本地 SDK 签名替代联调结论。

本轮工具请求记录、全量候选池及查询缓存随执行上下文传递，供反馈复用；不得放进返回给模型的完整上下文，也不跨用户共享。

更新 CLI 中依赖顶层 train_search 的重试判断。真实工具请求已经发出后，不因后续写入、摘要或规划失败重放整轮查询，避免重复付费请求。内部同参数缓存与日志写入失败测试共同验证。

复用 MeteredModel 记录每次模型调用；另记录工具名称、调用 ID、状态、耗时和是否命中本轮缓存。正常工具结果与失败结果一一对应。评估区分顶层 Agent 和内部工具，不继续要求四个旧 Agent 出现在执行阶段。

## 12. 验收场景

1. 只查火车/酒店/攻略：仅调度信息获取，工具调用正确，不触发行程规划。
2. 政策、记忆、偏好独立请求：保持原有能力，不强制进入信息获取。
3. 本轮修改偏好后查询：信息获取与规划看到合并后的偏好；临时偏好不意外持久化。
4. 缺日期、入住人数或无效日期：对应 Provider 不调用，返回明确缺失字段。
5. 模型同时调用多个工具：有效调用执行、返回配对，单项失败不吞掉成功结果。
6. 首批候选超预算：本地其他候选可重新筛选；不静默放宽预算。
7. 同参数补查/规划反馈：复用本轮数据；不同条件才重新请求；无服务端分页参数。
8. 候选多于 5、少于 5、不同席别、空列表：保留正确数量、差异和来源，全量候选不丢失。
9. 无数据源、超时、部分成功：状态在工具、信息获取、编排器和界面中保持准确。
10. 摘要或模型伪造价格、库存、候选 ID：事实显示和预算不采用伪造值。
11. 规划发现组合冲突：反馈只重查相关领域，随后重规划；触及限制或硬条件冲突时结束。
12. 解析无效模型动作、流式工具调用片段、未知工具：不执行不完整或未知调用，结果有界。
13. 后续记录写入失败：已经完成的真实火车请求不重复发送。
14. 行程历史从新条件对象保存；中间补查状态不作为最终行程保存。
15. 现有记忆、来源、预算、遥测回归通过；评估能识别内部工具失败。

自动测试使用假模型、假 Provider 和本地响应，不调用付费 API。实施后运行聚焦测试、完整离线测试、相关编译与 diff 检查。未进行真实接口联调时明确报告。
