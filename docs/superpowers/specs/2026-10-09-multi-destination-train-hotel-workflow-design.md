## 1. 用户目标与本次范围

用户希望先验证多目的地场景下的任务组织、Agent 循环、结果传递、跨段冲突、用户确认与断点恢复。本次只安排火车和酒店，不安排到目的地之后的具体活动。

以“上海 → 北京 → 杭州 → 上海”为例：

1. 任务一：上海到北京的火车，以及北京住宿。
2. 任务二：北京到杭州的火车，以及杭州住宿。
3. 任务三：杭州返回上海的火车，无酒店任务。

每个任务由独立 ID 标识，经历自己的规划循环。单段形成草稿后，可以推进下一段；后续安排有冲突时允许回改受影响草稿。所有任务形成草稿后检查全程，满足条件才统一标记校验通过并最终总结。

本次包含：

- 完整任务列表、任务状态、版本和依赖。
- 主 Agent 的任务决策循环、信息获取的工具循环。
- 火车及酒店独立查询结果，多段结果不覆盖。
- 出发、抵达、酒店入住离店及下一段出发的衔接。
- 重大冲突的修改建议、用户确认、断点保存与恢复。
- 可审计的消息、状态变化、停止原因及验证场景。

本次不包含：

- 景点、游玩活动、餐饮、旅游攻略、天气，以及景点开放或预约安排。
- 新增攻略 Provider、景点路线算法或新的业务 Agent。
- 订票、订房、支付；查询或选择候选不表示预订成功。
- 实际出发、抵达和游玩进度管理。
- 新的记忆自动删除策略、跨用户共享状态或历史数据全面迁移。
- RAG 内部改造、外部 RAG 项目及知识数据变更。

已有独立天气、记忆、偏好和 RAG 请求能力继续保留；本次多段测试不会自动调用天气、攻略或网页工具。用户仅要求单项查询时，保留现有按需直返路径。

## 2. 现有问题与代码事实

| 现状 | 问题 | 修改方向 |
| --- | --- | --- |
| `MainAgent.plan()` 初始分派，`finalize()` 收尾，最多一次补查 | 不能灵活逐段规划和从修改点恢复 | 主 Agent 根据当前状态多次选择动作 |
| `business_schedule()` 按 Agent 名合并调度项 | 不能用同一个信息获取角色表示多个独立旅程任务 | 保留前置角色调度；行程任务按任务 ID 执行 |
| `run.travel_conditions.update(query)` | 返程查询覆盖全程起点和日期 | 用户总体条件、任务条件和查询参数分开 |
| `domain_results[domain]` | 多段火车或多个城市酒店互相覆盖 | 核心结果按查询 ID 保存，再归属任务 ID |
| 信息获取候选选择按领域及最后一个查询匹配 | 早先查询的候选无法可靠关联 | 按查询 ID 及结果版本选择候选 |
| 行程日期 guard 会删除不符合条件的天数 | 错误状态可能造成“删掉已生成日期，再追问日期” | 返回明确冲突，不静默删除；输出使用统一校验结果 |
| `TrainOffer` 主要提供时钟字符串 | 不能仅凭 `21:05`、`09:24` 判断跨日或多日抵达 | 保存有依据的完整时间或明确未知 |
| 完成行程才进入历史；没有规划断点对象 | 用户答复后无法稳定从受影响任务恢复 | 新增独立的工作流状态快照 |

真实测评中，信息获取模型曾写对去程条件，但执行状态保留了被返程覆盖的字段。错误不是单纯的 JSON 语法问题；必须同时修复数据契约和状态合并规则。

## 3. 酒店能力与验收边界

当前 `76055fb` 已接入高德酒店地点搜索，返回地点 ID、名称、地址、坐标和来源；不能证明房价、房型、库存及取消规则。已有 `HotelOffer` 报价 Provider 注入路径仍保留。

本设计区分两种请求：

1. **酒店地点推荐**：可以选择有来源的 `hotel_place`，并安排拟入住、离店日期；实际价格、空房和入住规则仍未知。用户未要求验证报价和库存时，可完成“交通及酒店地点推荐”，不得宣称已完成预订或全部费用核实。
2. **酒店报价或空房验证**：必须有匹配日期、人数的报价证据。高德地点不能满足这类条件；返回 `partial`，列出未验证条件，不反复调用地点接口期待得到房价。

酒店地点搜索只需城市，不因缺人数或入住日期阻止独立地点查询。多段行程的时间衔接仍需要相应日期或住宿晚数；这些缺项用于行程判断，与酒店地点 API 的必填项分开。

预算未知不是预算为零。酒店地点不计入已知报价合计；全程预算只有在所有要求计入的费用都有可靠证据时才可标为已核实。现有价格精度、候选来源、密钥脱敏规则继续适用。

## 4. 方案及职责

采用“工作流任务结构 + 主 Agent 任务级决策循环 + 信息获取工具循环”。

| 角色 | 职责 |
| --- | --- |
| MainAgent | 创建完整任务提案，选择当前任务，提出查询目标、单段草稿、修改建议和结束动作 |
| InformationQueryAgent | 整理当前任务条件，调用火车/酒店工具，必要时补查，返回事实、执行情况和小结 |
| Harness | 分配稳定 ID，校验消息，限制作用域，执行动作，保存结果和状态，检查冲突，管理断点及最终输出 |
| 偏好与记忆角色 | 沿用已有职责；按需在相关查询前执行，不因每段循环重复执行 |

RAG 保持原协议和实现，本次多段验收不调用它。所有新业务事实必须来自工具结果或用户明确提供的信息。

主 Agent 接口拟为 `initialize(context)` 和 `step(context)`：前者创建工作流提案，后者每次返回一个决策。旧单项查询入口通过适配继续使用；不得在旧收尾链之后再运行一套重复工作流。

## 5. 工作流及任务状态

工作流状态：`running / needs_input / completed / partial / error`。

任务状态：

| 状态 | 进入条件 |
| --- | --- |
| `pending` | 尚未规划，或条件更新后待重新规划/检查 |
| `running` | Harness 正在执行该任务的查询或草稿修订 |
| `draft` | 当前版本已有草稿，尚未通过全程校验；可以包含明确资料缺口 |
| `needs_input` | 当前问题必须由用户补条件或批准修改 |
| `validated` | 当前版本在全程检查中满足其请求要求和衔接条件 |

正常转换：`pending → running → draft`，然后推进后续任务。必要时 `running/draft → needs_input`；用户答复后按更新后的版本恢复到 `pending`。已保存草稿不因状态重置而删除，但必须标明其版本失效。

所有任务形成草稿后，进行全程校验。全部满足条件时，Harness 原子地把当前任务版本标为 `validated`，工作流转为 `completed`。后续修改已完成规划时，相关任务恢复为 `pending`，工作流重新进入 `running`。

不能使用“没有 draft”“draft 少于两个”或模型自行返回 `planning_complete=true` 作为成功条件。状态决定待办范围，校验事实决定能否完成。

遇到无法补齐的资料缺口或资源上限可以以 `partial` 结束本轮，任务仍可保留草稿；结束调用不等于规划成功。

### 6.1 默认值、推导值及追问边界

缺少字段不等于必须追问。先解析用户原文和当前工作流上下文，再应用已有适用条件、可靠推导及默认配置。只对会阻止当前目标、无法合理默认或存在重大歧义的字段询问用户，并把相关缺项合并成一次简短问题。

以下默认值为本次设计的拟定初值，随本文审阅；不表示用户已经明确提供这些条件：

| 字段 | 缺少时的处理 | 是否直接追问 |
| --- | --- | --- |
| 火车人数 `passengers` | 用户和当前上下文均未提供时，默认 1 人 | 不追问，在结果中简短注明按 1 人查询 |
| 酒店人数 `guests` | 未单独指定时，沿用当前旅客人数；旅客人数也未知时使用默认 1 人 | 不追问；地点搜索本身也不依赖人数 |
| 预算 | 不设置额外预算上限；保留用户已给限制 | 不因没预算而追问，不凭空设为 700 或 500 元 |
| 席别 | 无要求时不加硬性席别限制，按实际候选比较 | 不追问，不把默认排序当成用户强制二等座 |
| 酒店品牌 | 使用适用的已保存偏好排序；没有偏好则不限制 | 不追问，不把品牌偏好提升为必须满足的限制 |
| 候选视图数量 | 每查询默认最多 5 个，沿用现有配置 | 不追问 |
| 起始日期 | 从用户明确日期、当前行程日期或“明天”等相对日期解析 | 无法确定且要查具体火车时才问；不静默改为今天 |
| 后段出发日期 | 在用户允许的时间安排范围内，结合前段住宿和可靠抵达日期提出 | 能可靠衔接则继续；改变固定日期或有重大冲突时才问 |
| 入住、离店或住宿晚数 | 使用用户条件及全程时间分配；用户把安排交给 Agent 时可给明确标注的草稿建议 | 地点查询不问；精确报价缺必要日期且无法安排时才问 |
| 供应商价格、库存、抵达时间、入住规则 | 未取得可靠证据则保持未知，按需要补查或报告缺口 | 不能用默认值伪装成事实，也不把接口缺口全部转为用户问题 |

例如只要求“帮我安排”、已给起始日期并允许灵活停留时，Agent 可以提出住宿区间并据此查询；如果用户没有允许灵活日期且缺少会决定后段日期的停留条件，再一次性询问住宿晚数或可用天数。只需要城市酒店地点时，即使所有日期都未确定，仍可先查询酒店地点。

字段来源和覆盖规则：本轮用户明确的任务要求优先于适用的全程一般要求；当前工作流已确认条件优先于可适用的历史信息、推导及默认值。任务特例必须确实来自用户，不允许 Agent 把自己偏好的方案当成例外。

`effective_conditions` 保存本次实际采用的条件，供工具参数和人数、预算校验使用；`field_sources` 保存对应来源，取值 `user / context / preference / derived / default / proposal`。默认及建议不写入 `confirmed_conditions`，不自动存为长期偏好。默认值与建议的使用不等于完成预订，也不要求用户先确认每个普通默认值才能查询。

来源示例只列人数；实施时对影响日期、筛选和预算的字段同样记录来源及必要依据。字段存在相互矛盾的用户信息时不得用默认值覆盖矛盾，而应确认冲突。

用户后续说明“实际是 3 人”时，用新人数更新有效条件，增加受影响任务版本并重新检查人数、费用和库存；可复用不受人数影响的地点资料。单纯缺失预算、席别、品牌不得被加入 `missing_fields` 阻止循环。

## 7. 查询及候选保存

每个查询保存 `id / task_id / task_revision / domain / parameters / constraints / result_revision / status / items / source / fetched_at / execution`。

- 支持同一任务多个火车、酒店查询，领域本身不是结果主键。
- 新参数创建新查询 ID；相同参数刷新保留同一查询 ID 并增加结果版本。
- 完整候选池由程序保存，给模型的视图每个查询默认最多 5 个候选。
- `candidate_offset` 读取本地池，不假装供应商支持分页或数量参数。
- 同参数有效缓存可以跨任务复用，但每次任务消费仍记录自己的归属和版本。
- 刷新失败不覆盖已取得的来源事实；保留旧候选必须标记其取得时间和待重新确认状态。
- 后续任务、后续领域和失败查询都不能抹掉前面已取得的结果。
- 单项查询兼容输出可以映射为旧 `domain_results`，多段核心状态禁止靠这个单值映射保存全程。

## 8. Msg 传输协议

所有消息记录 `schema_version / message_id / workflow_id / turn_id / task_id / task_revision / in_reply_to`，由 Harness 添加并校验。任务未创建时 `task_id` 可以为 `null`。

业务内容统一用 Python 字典契约；通过 AgentScope `Msg` 时序列化放入 `content`。现有信息获取 `.run(context, run)` 与其他角色 `.reply(Msg)` 通过适配器使用同一内容协议，不强制修改冻结的 RAG 接口。

下列 JSON 展示 `content` 的业务负载，公共关联字段由 Harness 附加，不要求模型自行生成。接收结果时必须核对任务归属及版本；旧版本的异步返回可以保留在记录中，不能覆盖已经更新的任务。

### 8.1 主 Agent 初始输出

输出 `workflow_proposal`：路线、总体条件、按顺序排列的任务提案及依赖。不能先生成一次独立意图分派，再重复生成同一套行程任务。Harness 校验路线、ID、依赖、酒店作用域及日期后保存完整工作流。

### 8.2 子 Agent 输入

```json
{
  "type": "task_request",
  "task": {
    "id": "task_001",
    "revision": 1,
    "goal": "查询上海到北京火车及北京酒店",
    "requested_domains": ["train", "hotel"],
    "query_requests": []
  },
  "context": {
    "original_query": "上海去北京，再去杭州，最后回上海，只安排火车和酒店",
    "confirmed_conditions": {},
    "effective_conditions": {"passengers": 1, "guests": 1, "constraints": {}},
    "field_sources": {"passengers": "default", "guests": "derived"},
    "effective_preferences": {},
    "workflow_overview": [],
    "current_task": {},
    "previous_boundary": {},
    "relevant_results": [],
    "session_summary": "",
    "recent_messages": []
  }
}
```

`workflow_overview` 包含全部任务的目标、状态、版本及顺序；`current_task` 展开当前条件。`query_requests` 使用解析、推导和默认合并后的有效条件。只有当前查询仍缺必要参数时，才不发起该查询并返回缺项；其他可执行查询继续。允许默认 1 人，但来源为 `default`，不把它当成用户已确认人数。

### 8.3 子 Agent 返回

```json
{
  "type": "task_result",
  "task_id": "task_001",
  "task_revision": 1,
  "agent": "information_query",
  "status": "partial",
  "summary": "当前段的资料获取小结",
  "query_results": [],
  "missing_fields": [],
  "issues": [],
  "execution": {
    "model_calls": 0,
    "tool_calls": 0,
    "cache_hits": 0,
    "failed_calls": 0,
    "elapsed_ms": 0,
    "stop_reason": null
  }
}
```

该例只说明字段，数值不是实际执行统计。`query_results` 为程序核实的工具结果，包含查询参数、候选、来源及执行状态；不信任模型改写的价格或库存。`summary` 是子 Agent 对本任务的资料小结，不取代结构化结果，也不代表全程完成。

子 Agent 状态使用 `ok / partial / needs_input / unavailable / error`，与任务 `draft / validated` 状态分离。

### 8.4 再交给主 Agent 的上下文

必须包含：用户原文、用户确认条件、有效条件及其来源、完整工作流任务列表、当前任务、最新子 Agent 结果、当前草稿、前后任务的时间边界、相关候选视图、未解决问题，以及调用资源剩余量。

完整任务规划不因进入下一段而丢失。当前任务候选展开，其他任务保留草稿要点和已选候选的必要事实；需要比较时再展开相关细节。程序保留完整结果，不把所有历史重试数据在每轮重复发送。

### 8.5 主 Agent 决策输出

按 `action` 校验不同必填字段，不依靠自由文本猜动作：

| action | 必填业务内容 | Harness 行为 |
| --- | --- | --- |
| `dispatch` | 当前任务 ID、目标、查询请求 | 执行信息获取，保存结果，再调用主 Agent |
| `draft_task` | 任务 ID、当前版本、火车/酒店草稿、任务小结 | 校验并保存草稿；选择下一任务或进入全程检查 |
| `ask_user` | 问题、原因、涉及任务、可选修改建议 | 保存断点，结束本轮并等待用户 |
| `validate_workflow` | 当前工作流版本、跨段分析 | 执行确定性全程检查，回传检查结果 |
| `finish` | `completed/partial`、最终回答及缺口 | 检查交付条件后形成统一输出 |

`draft_task` 是明确的进度动作，避免把“没有工具调用”或“一次子 Agent 返回”直接当成完成。保存草稿也不立即把任务标为全程校验通过。

主 Agent 决策不能任意覆盖其他任务状态；所有状态转换、版本递增和候选引用由 Harness 处理。

## 9. 循环调度与结束

正常链路：

```text
创建完整任务列表
→ 任务一：查询/补查 → 主 Agent 草稿 → 单段检查
→ 任务二：继承必要边界 → 查询/补查 → 主 Agent 草稿 → 衔接检查
→ 任务三返程：查询/补查 → 主 Agent 草稿 → 衔接检查
→ 全程校验
→ 有冲突则回到受影响任务；否则统一完成并总结
```

同一任务可多次调用信息获取；每次信息获取内部仍按“模型选择工具 → 工具结果 → 模型观察”循环。已知参数互不依赖时，当前任务的火车和酒店查询可以并行；需要抵达日期才能确定酒店区间时先查交通。

草稿有不会阻止下一段判断的资料缺口时，可明确保留缺口后推进；例如用户仅需地点参考时房价未知。若未知抵达日期影响下一段出发或酒店入住，不宣称可行，先补查或询问用户。

结束规则：

1. `completed`：全部当前任务版本经过全程校验，路线完整、要求满足、时间衔接成立，无重大未决冲突。
2. `needs_input`：缺阻止当前目标且无法可靠推导或采用合理默认的必要条件，或需要用户批准改变已确认日期、预算、目的地、住宿要求。普通默认项不触发暂停；相关缺项合并询问。保存断点后返回问题；等待期间不保持模型循环运行。
3. `partial`：供应商能力不足、无可行且获授权的补查、重复执行没有新信息，或达到资源上限。返回已有草稿及缺口，不假装所有任务完成。
4. `error`：无法解析/校验到可执行动作或不可恢复执行错误。保留已有状态及安全错误信息。

Harness 必须拒绝或反馈非法 `finish`，而不是因为模型要求结束就跳过全程检查。没有待查询任务且草稿齐全时，应进入校验，不反复查询只为把所有 `draft` 改掉。

资源初值属于可调整实施参数：建议每任务最多 3 次信息获取执行；沿用每次信息获取最多 6 次模型、10 次工具、单工具 30 秒。主 Agent 决策上限按任务数计算，初值 `4 × 任务数 + 4`；整轮工具上限初值 `10 × 任务数`，另有可配置整轮总时限，调用开始前检查剩余预算。

相同任务版本、相同参数、相同动作且观察没有变化时停止重复执行；有可靠瞬时错误依据时至多额外重试一次。未配置服务或不具备房价能力不重试以求成功。用户后续回复开启新的调用预算，但继承工作流和断点，不重放已完成查询。

执行次数限制按当前用户回合累计，不因为进入下一个任务、修订草稿或重新调用子 Agent 清零；工作流另保存跨回合累计统计用于审计。

## 10. 时间、住宿与全程校验

- 查询参数中的 `departure_date` 只属于对应查询及任务，不回填全程起始日期。
- 火车完整出发时间可由查询日期和可靠发车时刻组合；抵达日期只依据供应商明确日偏移、可靠总耗时等证据。信息不足时 `arrival_at=null` 并记录时间待核实，不靠时钟先后强行断言“次日”。
- 选择夜间跨日车次后，住宿区间和下一段出发需按实际可验证抵达日期检查，不默认出发当晚已到目的地。
- 日期只有日没有时，不虚构精确到分钟的边界。
- 用户已指定的下一段日期不自动改变。可调整的建议日期根据前段住宿区间提出，并记录推导来源。
- 酒店 `check_in < check_out`；下一段不能在抵达前出发。未知酒店具体入住/退房时刻保持未知；不能把地点 API 当作这些规则的依据。
- 本次无活动安排，不生成景点行程、活动时长或虚构市内通勤时间。
- 只有用户明确允许日期灵活且查询参数确实改变时才补查新日期；否则给建议并询问用户。
- 全程检查包括路线连续、返程覆盖、任务依赖、候选查询归属、时间证据、住宿区间、人数和预算要求，以及事实来源。
- 时间、预算和引用的确定性问题由程序校验；模型可以提出调整，但不能通过解释绕过校验。
- CLI 展示与最终保存使用同一份已校验结果，不再次运行会删日期或改写行程的另一套 guard。

## 11. 冲突、断点与从修改点恢复

重大冲突先返回原因及具体修改建议。建议必须标明是提案，不代表替代车次、房价或库存已经验证。

断点至少保存：`reason / affected_task_ids / resume_task_id / question / suggested_changes / expected_workflow_revision`。工作流转为 `needs_input`，保存成功后再返回用户。

用户答复后：

- 修改任务一：任务一增加版本；后续依赖任务标为待重新检查，从任务一恢复。
- 修改任务二：保留未受影响的任务一；任务二增加版本，返程任务待重新检查，从任务二恢复。
- 拒绝建议：保留原要求，尝试其他已获授权候选；没有可行方案时如实返回部分结果。
- 目标不明确：先确认具体要改哪段及什么条件，不猜测用户授权。
- 多个进行中规划：按工作流 ID 恢复；无法明确关联时询问选择，不修改错误行程。

重新检查不等于全部重新查询。参数没变且资料有效时可复用；日期、人数等变更时只重查相关查询。旧版本继续用于审计，但不进入新版本候选选择。后续修订反过来影响前段时，先检查并取得必要用户同意。

返程没有候选与接口不可用必须区分。接口失败不得陈述“那一天没有火车”。只有查询成功且已知筛选范围内无合格结果时，才能说明该范围内未找到满足条件的车次。

## 12. 保存与恢复

新增 `WorkflowStore` 保存按用户隔离的结构化快照，建议路径 `data/memory/<user_id>/workflows/<workflow_id>.json`，通过原子替换写入。快照包含全部任务、当前版本、草稿、查询结果或持久化候选索引、断点、资源和校验摘要。

读取用户答复和提交状态更新时核对预期工作流版本；同一工作流更新需串行或使用版本比较，防止不同会话及迟到的执行结果覆盖较新状态。原子写入保证文件完整，版本检查保证业务更新不会丢失。

候选引用所指数据必须一并持久化；恢复后不能只有 ID，没有候选事实。恢复时对价格和库存标注取得时间，需要时刷新，不能视为永远有效。

会话 `state.json` 只保存活动工作流索引及已有对话摘要，避免把压缩摘要与业务状态混在一起。短期记忆压缩不改变任务状态、用户确认条件、已选候选或断点。

`events.jsonl` 继续追加消息和阶段事件，`runs.jsonl` 继续记录模型和整轮耗时；工作流快照用于运行恢复，日志用于追踪，两者不能互相替代。恢复不重放已记录完成的付费查询；状态写入失败时不自动从用户原文整轮重跑。

本次保存进行中状态，不制定新的自动清理期限，不删除历史记录。长期偏好保持现有存储；完成规划可沿用历史行程出口保存工作流引用和摘要，区分规划记录与实际旅行经历。
