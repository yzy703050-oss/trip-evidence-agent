## 已纳入立即修改：会话日志不再重复保存完整 TripPlan

2026-10-12 用户指定立即处理，优先于下文两项后续改进。当前状态：已随 SQLite 改造完成；本节保留问题背景、实施范围与验收方向，正式规格与测试证据见上文链接。

改造前的问题：CLI 将整轮返回结果序列化写入 events.jsonl，workflow 模式的结果包含完整 TripPlan；同一份行程已由 workflows/<id>.json 保存最新状态，会话日志又随轮次积累完整行程副本。已有上下文投影避免了把这些副本原样传给模型，本项解决的是重复持久化及原始事件的内存、读取开销，不应描述为修复完整 workflow 泄漏到提示词。

立即修改范围：

- 新写入的会话最终回复不再嵌入完整 workflow 对象；保留面向用户的回复、必要业务摘要和 workflow_id/workflow_revision 引用。具体字段白名单在正式设计中确定，以历史对话、压缩和恢复所需信息为依据。
- 完整 TripPlan 由 WorkflowStore 数据库门面负责，内容与小结同次事务提交；版本校验和断点恢复保持原有行为。精简仅作用于会话保存副本，不原地删除本轮返回结果中的 workflow，不影响展示、last_result 或调用方读取。
- 兼容现有含完整结果的旧事件，使已有历史会话仍可读取、压缩和恢复。本项不直接清理旧日志、不改查询记录自身的 history、不新增完整快照副本；历史数据瘦身可另行评估。
- 本项已纳入用户确认的 SQLite 存储层改造，不等待 AgentScope 移除或面向用户的 TripPlan 只读查询，不重复实施一轮文件存储修补。

验证与完成条件已满足：红绿测试验证真实 CLI 保存路径的新最终事件不含完整 workflow，而返回结果与权威行程记录仍完整；覆盖行程创建、修改、部分完成后的保存，以及新旧事件读取、会话压缩和重启恢复兼容。500 个候选的合成样例中，完整结果 533,397 字节，精简事件内容 219 字节；该样例只说明保存内容的差异，不代表生产性能。

## 后续改进：完全移除 AgentScope

2026-10-12 用户确认加入后续改进方案，状态为待规划、未实施。本节记录改进方向，不作为新的行为规格；正式实施前按项目流程创建 OpenSpec 变更，完成技术复核和详细实施计划，并由用户选择执行方式。

目标：保留自研 Agent 内核，完全移除 AgentScope 的导入与直接依赖，改用 OpenAI 官方 SDK 和项目自己的轻量接口。当前主要使用框架的模型封装、AgentBase、Msg 和初始化入口；未主动使用其 Hooks 扩展机制。

迁移范围：

- 模型适配：以 AsyncOpenAI 为底层接入现有 OpenAI 兼容服务，提供项目自己的模型接口，承接文本、流式响应及工具调用。核对完整响应收集、工具调用 ID 与参数、输出用量及预算统计语义，避免执行尚未收集完整的工具参数。
- Agent 与消息接口：移除 AgentBase 继承，以项目接口描述 reply/run 能力；替换 Msg，调整懒加载注册器的类型识别及 Harness 的输入输出适配。保留现有主 Agent、ReAct 循环、Runner 和业务状态机。
- 入口与依赖清理：移除 agentscope.init()、框架配置及相关引用，更新 CLI、健康检查、测试、评测脚本和文档；显式声明直接使用的 SDK 依赖，只清理确认未被其他功能使用的依赖。
- RAG 边界：独立 RAG 项目的实现不纳入本次改进。若本仓库现有问答接入或辅助脚本引用 AgentScope，仅处理完全移除框架所需的接口兼容，不重构检索逻辑。

验证与完成条件：

- 在不安装 AgentScope 的干净环境中，项目入口可启动，运行代码、测试及评测脚本不再导入框架。
- 按正式实施计划执行适用的 TDD，验证模型响应适配、流式工具调用、预算统计和异常路径，并运行相关回归测试；确认规划、修改、候选引用、跨会话恢复及用户隔离行为符合现有规格。
- 对比迁移前后的启动/导入耗时、进程内存和干净环境依赖规模；收益依据测量报告，不把导入耗时差异当作每轮对话加速，也不预先承诺模型 Token 费用下降。

已有初步观测：本机独立 Python 进程各采样三次，OpenAI SDK 导入耗时中位数约 0.62 秒，AgentScope 模型模块约 1.58 秒。该观测只反映本机导入开销；内存与安装体积尚未测量，不能据此宣称整体运行性能大幅提升。

## 后续改进：TripPlan 只读详情与候选查询

2026-10-12 用户确认加入后续改进方案，状态为待规划、未实施。本节记录需求方向；正式实施前创建 OpenSpec 变更，确认读取接口与场景，完成技术复核和详细实施计划。上文“不新增主模型读取工具”是已归档变更的范围决定；本项未来若引入读取动作或工具，应在新变更中明确设计，不修改旧变更记录。

现状：完整 workflow（业务概念为 TripPlan）保存查询记录、候选与草稿，已有候选分页辅助函数；主 Agent 正常发现行程时只接收结构化小结，目前缺少面向用户的独立只读详情及完整候选查询入口。主提示词仍引用小结不再提供的 known_workflows.saved_plan，应在实施中协调提示词与实际数据契约。

目标场景：用户可以查看指定旅程或路段的安排、已选酒店/车次、相关查询依据，以及此前查询并保存的酒店或火车候选，例如“查看上次北京行程第二段的全部酒店候选”。

改进范围与边界：

- 先通过小结定位目标 TripPlan，目标有歧义时澄清；选中后按所需路段和领域读取结构化细节，不将所有完整旅程载入提示词。
- 提供独立只读查询路径，具体采用 Harness 动作、工具或其他接口留待技术设计确认；查看详情不进入重新规划循环、不推进任务状态、不改业务版本、不重新请求供应商。
- 候选按页提供，并说明已保存候选总数与当前页范围；“全部候选”指已保存查询结果中的候选，不表示供应商的全部酒店、实时空房或最新价格。明确区分当前任务版本的有效候选与历史/失效结果，默认读取范围及历史查看方式在正式规格中确认。
- 保留来源、查询时间及必要的未核实说明；没有保存所需内容时如实告知，不凭摘要补造细节。用户明确要求最新数据时，另走刷新路径，不把历史读取冒充实时查询。
- 校验用户归属及旅程、任务、查询引用，处理目标不存在、无候选、页范围无效和读取期间版本变化；不跨用户返回数据。

验证与完成条件：为详情读取、候选分页、多旅程澄清、版本与用户隔离编写有意义的测试；验证读取前后业务状态及版本不变、供应商请求为零、精简上下文仍按需构造。测试与规格核对通过后，才将本项标记为已实施。
