## 请求编排

WorkflowRunner 是整个请求的程序协调器，负责偏好/政策前置、主模型调用、任务与工具安排、状态推进、全程校验和局部修复。ExecutionHarness 只负责兼容转交；ToolExecutor 负责接口和单工具超时，batch_execution 负责独立作用域并发、额度预留、依赖屏障和串行归并，result_views 负责无模型清洗。

主 Agent 首次识别意图与目标，生成 schedule/query_plan；工具资料取得后，主 Agent 一次提交各 task 的候选引用和回复模板。程序完成引用、版本、日期、费用与强制政策检查；有效时保存并渲染，无效时反馈实际冲突，按模型选择的范围修复。正常旅游回放两次主模型调用；缺口、冲突、非法输出和实际依赖可以增加调用，不保证所有请求都是两次。

## 偏好与政策

明确长期偏好更新、查询、撤回和历史读取是普通工具，零模型调用；混合请求先保存再重读偏好。长期记录保留自然语言条件、来源、状态及证据，定向操作使用记录 ID。临时条件不写入长期记忆。

偏好分析 Agent 合并旧 preference/memory_query 的分析能力：首次三份唯一有效行程后总结一次，持久化完成标记；六份、十份和恢复不会重复自动总结。明确重新分析可以触发；人工记录、撤回保护和强制政策不能被推断偏好覆盖。

政策 Agent 继承 rag_knowledge 检索入口，一次模型理解并提取带真实引用的结构化 JSON。程序核对金额/单位、来源、适用对象与生效日期；城市和行程日期在 schedule 已知后再核对。审批、未知规则、资料冲突或检索失败保留缺口，不能宣布合规。RAG 底层不重构。

information_query 的源代码与旧设计保留，当前所有运行路径均静默；旧偏好/记忆模型也不参与当前请求。天气、火车、酒店、攻略、网页的已迁移查询直接走工具。

## 查询、状态与局部修改

模型视图按领域白名单清洗、去重和限长；候选默认五条，天气每城市/日期保留一条。完整规范化结果保存在缓存，来源、时间及未核实约束保留；展示字段精简不能破坏校验所需的地点和时间证据。

独立查询并行，显式 depends_on 使用 request_id 指向前置请求；依赖失败只阻止相关请求。已开始请求的身份在供应商调用前保存，已完成结果逐项归并。旧 querying 容器映射 empty 时，仍保留未知完成记录，避免恢复重发。

| 层级 | 状态 |
| --- | --- |
| TripPlan | running、completed |
| task | pending、draft、validated |
| 查询容器 | empty、ready、failed |

needs_input、依赖等待、在途等由字段派生；draft_stage 区分查询和选择草稿。失败、暂停和取消原因保留，不因顶层映射 running 自动恢复或误计有效历史。

已有行程修改合并意图与目标定位，先筛完整缓存再构造有界候选。只改选择且证据充分时自动校验保存；参数变更、过期或显式刷新时仅补受影响领域。报价不能通过改日期伪造。重绑定保留历史；未通过的修改暂存 pending_amendment，并保留上一有效方案，恢复先检查未知在途请求。

## 未来修改方案：信息获取 Agent 与工具轻量清洗

2026-10-13 用户要求记录，尚未实施。将信息获取能力交给 Agent：它根据用户本次要求、长期偏好及已提取的政策约束，自主安排工具查询、读取详情、补充证据，并把总结性语言与结构化事实一起返回主 Agent。范围包括已有信息获取领域，不局限于酒店位置分析。可以复用保留的 information_query 设计，但不直接恢复旧的多轮分段查询流程；当前 information_query 继续静默。

### 职责与流程

主 Agent 负责生成旅行任务、传递明确条件与资料需求、最终规划整趟旅行，以及定位用户后续修改。信息获取 Agent 负责如何取得任务所需的信息、比较候选与约束、发现资料缺口和信息层面的冲突；不提交 TripPlan、不决定跨段修复、不修改用户固定日期、预算、路线或强制政策。

偏好读写仍走现有记忆工具；信息获取 Agent 使用已经读取的偏好，不重新总结长期记忆。政策 Agent 仍负责检索、理解并返回带来源的政策 JSON；信息获取 Agent 使用这些硬约束查询与比较，不自行放宽或重新解释审批要求。偏好是软约束，无法同时满足时说明取舍，不能覆盖政策。

拟议链路：主 Agent 生成任务与信息需求 → 信息获取 Agent 根据要求、偏好和政策调用工具 → 整理自然语言说明和结构化证据 → 主 Agent 规划或局部修改 → 程序校验、保存与渲染。

独立工具查询可并行；有依赖的查询按实际依赖执行。已有缓存足够时直接读取和重组，缺少证据时才补查受影响范围。工具超时、并发隔离、缓存、版本及调用预算仍由程序负责，距离和费用等确定性计算使用程序工具。未增加有效证据的重复查询应停止，并返回缺口。

### 减少搜索工具的数据裁剪

工具保留基础清洗：响应结构与字段类型检查、日期/金额/坐标规范化、去重、无效记录排除、敏感凭证移除、来源与获取时间记录。不再默认把提供给信息获取 Agent 的结果裁剪成仅含酒店名称和地址的极简模型视图。

对酒店保留行政区、位置坐标、评分，以及接口实际提供的详情、设施、房型、报价、库存、取消规则和相关链接；其他领域同样保留与用户条件、偏好及政策判断有关的事实。字段不存在时标记未知，不能补造。高德地点接口仍不能把 business.cost 当成对应入住日期的房价，也不能从酒店名称推断海景房或空房。

减少清洗指减少有意义字段的删除，不是取消数据质量检查，也不是把所有原始响应无界塞进上下文。完整响应与规范化证据保存在缓存；信息获取 Agent 可分页读取候选、按 ID 读取详情。较长资料提供带截断标记的摘要和完整内容引用。主 Agent 接收经过信息获取 Agent 整理的有界总结及事实引用；需复核时可以读取原证据。

程序按可靠事实筛选硬约束时，保留返回数、排除数与排除原因，供 Agent 判断是否需要扩大搜索或补证据。未知条件不能当作已满足，软偏好不能作为默认硬过滤条件。

### 返回主 Agent 的内容

返回结构化 JSON，包含自然语言 summary、候选与查询结果引用、与各项要求对应的检查、政策来源、冲突、未核实项和必要的后续建议。总结帮助主 Agent 理解资料，但不能替代用于程序校验的候选 ID、结果版本及原始事实。

以下仅为返回结构示例，字段将在未来 OpenSpec 设计阶段确定；名称、数值和引用均为示意，不代表当前运行结果：

```json
{
  "task_id": "task_123",
  "summary": "候选酒店位置接近海滩；价格、步行距离和夜间安静程度尚未核实。",
  "candidates": [
    {
      "ref": {
        "query_id": "query_123",
        "result_revision": 1,
        "candidate_id": "hotel_123"
      },
      "checks": [
        {
          "requirement": "靠海",
          "constraint_type": "preference",
          "status": "supported",
          "summary": "距所选海滩直线 420 米，未核实步行路线。",
          "facts": {"distance_m": 420, "distance_type": "straight_line"},
          "evidence_refs": ["map_result_123"]
        },
        {
          "requirement": "酒店每晚不超过 500 元",
          "constraint_type": "policy",
          "status": "unknown",
          "summary": "当前酒店接口没有入住日期对应的房价。",
          "policy_rule_id": "hotel_max_nightly_cny",

        }
      ]

```

## 2026-10-13 已实施：条件强度和冲突分流

按用户确认“也做”实施 condition_strengths 与冲突规则。日期和住宿晚数使用 hard/soft，与来源分开；旧行程兼容，全局硬边界与政策不允许模型降级。用户明确修改条件可更新强度，模型仅能受控调整软日期。

删除火车工具自动顺延后一天/后两天的规则，由主 Agent 协调去程、住宿和返程，使用 repair_tasks.task_updates。程序验证范围、版本和硬边界，仅查询新日期所影响的领域，旧报价和余票不能改日期沿用。日期补丁中的非法冲突代码返回反馈，不能执行查询。

已证实的固定日期冲突保存具体条件与证据并等待用户，顶层保持 running，使用 stop_reason=user_input_required和checkpoint派生等待。用户明确修改后恢复原行程。失败、空结果及未知事实不是自动要求放宽日期的依据；已有其他可行候选时先重组。接口缺字段、失败、纯报价超标由主 Agent 说明限制并停止同一缺口补查，数据清洗保持原样。

验收详情及实际模型成本见 [验收记录](../evals/2026-10-13-tool-evidence-boundaries/report.md)。上面的信息获取 Agent 与减少工具数据裁剪仍属于未来修改方案。

## 2026-10-13 已实施：实际上海行程与首次完整提案

无明确出差信息时不自行套用企业政策或增加身份、住宿报价门槛。用户明确的硬报价/预算及已确认适用政策仍校验；没有这些要求则可推荐hotel_place，房价、房型和空房未知作披露。去程失败时仍保留已有酒店与返程候选，返程为暂定选择，衔接需待抵达核实。回复按当前任务版本、容器引用及筛选结果区分失败、空结果、条件排除、未选定及旧证据，不再将已有候选写成没查到。

首次提案同次生成完整路线及各住宿任务的晚数或合法入住离店日期，未知供应商时刻仍留空。模型建议保留proposal/soft，用户固定条件不被覆盖；有效首次输出不调用repair_proposal，无效输出仍只用现有有限修正兜底，没有程序固定默认晚数。

实际保存数据选择回放保留登巴客栈和D352，仅去程缺口阻塞；一次调用5,829 token、3.32秒。普通、固定日期、多目的地完整模拟供应商流程均两次真实模型调用、零修正；完整请求8,562/8,460/10,725 token。记录见[首次提案验收](../evals/2026-10-13-first-call-proposal/report.md)和[实际上海回放](../evals/2026-10-13-shanghai-selection-replay/report.md)。未改变工具清洗、分页或未来信息获取Agent方案。
