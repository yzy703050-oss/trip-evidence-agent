# 主Agent提示词优化实测

日期：2026-10-13。结论：补回必要结构边界后，最终版本的5类完整请求及5项复杂场景回放均满足各自预期。普通请求继续使用2次模型调用，同条件测试总token下降约33.1%。没有进一步缩减候选数量、候选字段或完整缓存。

## 修改内容

- 首次规划采用紧凑契约，省去重复的完整schema和说明；完整结构校验、金额类型校验、无效决定/提案修复仍保留。
- 根据已知上下文加载已有旅行的匹配、局部修改、澄清、刷新和只读读取格式；没有旧旅行目标时保留一般意图识别和缺目标澄清。
- 批量选择合并重复规则。仅提交时只传工具能力说明；开放查询时传相关实际schema，保留分页参数、到达条件工具和相关天气工具。Runner内部工具清单及allowed_actions不变。
- 明确条件层级、目的分类、单段出发日期、返程目的地及来源/强度边界；不能默认出差、把去程日期全局继承到返程或要求普通酒店必须有报价。
- 候选、程序校验和最终事实渲染保持原行为；正常2次是目标，复杂修复允许必要额外调用。

代码：agents/travel_prompts.py、agents/main_agent.py、agents/model_contracts.py、agents/context_projection.py。

## 首轮失败与修正

根目录保留首轮5项失败，summary.json及对应model-responses.json、result.json没有覆盖：

- 普通旅行：模型把origin放入条件/强度，触发提案修复；全局departure_date也使返程继承去程日期，出现日期冲突。
- 固定日期：模型把destination、purpose等放入confirmed_conditions，触发结构修复。
- 多城市：模型无依据把目的定为business，引入政策未核实阻塞。
- 去程失败/仅换酒店：无效条件及返程destination=null导致初始化失败，后续修改没有可用旅行目标。

解决方式是补回关键结构与语义边界，未放松程序校验，也没有用自动重试抹掉失败。修正后的5类请求首轮提案均有效，没有repair_proposal/repair_decision额外调用；酒店修改使用原有amend_saved_trip模型阶段。
