# 条件强度、日期调整与查询停止验收

2026-10-13。变更：clarify-tool-evidence-boundaries。单代理、当前目录实施。

## 实现行为

- condition_strengths 使用 hard/soft，与 field_sources 分离；目前限定日期和 nights。旧记录保守解释，全局硬边界不能被任务软化。用户明确更新可改条件，模型修复仅能修改软条件。
- 工具不再自动查询后一天、后两天。主 Agent 使用 repair_tasks.task_updates 协调软日期，程序验证任务、版本、实际冲突代码、固定抵达期限和硬晚数，再失效受影响证据。去返程使用各自 departure_date。
- 新日期允许定向查询；旧车次和报价事实不改写。字段缺失、接口失败、报价超标不能作为同一缺口反复查询的理由。
- 明确日期自相矛盾，或完整有效保存候选均不能满足固定抵达期限时，保存 hard_condition_conflict 问题和证据，返回 needs_input。TripPlan 仍 running，stop_reason=user_input_required。用户修改后恢复原行程。
- 空结果、未知抵达、失败/失效证据不是证明不可行。已有其他候选可满足时不自动询问。检验的是当前已查范围，不声称覆盖全市场。

## 保留的失败与修正

1. 首轮报价超标：模型正确说明缺口，却省略 allow_repair=false，可能继续修复。提交示例增加显式停止标记，开放动作提示明确指出只写缺口不等于停止。复测通过。
2. 首轮软日期：模型提交无车方案并停止，误认为尚无其他日期的查询依据。明确区分成功空结果与能力失败，说明 soft授权构成新日期参数依据；用户要求改期时先提出协调日期补丁。
3. 第二轮软日期：模型提出18/20日，但编造 conflict_codes=no_return_candidates。提示直接列出实际可用 blocking代码，程序仍拒绝虚构代码；非法修复反馈原问题，在既有调用上限内允许纠正，未执行供应商。第三轮通过。

原始失败、成功输出及 usage 分别保存在同级目录和 `../2026-10-13-tool-evidence-boundaries-follow-up/`、`../2026-10-13-tool-evidence-boundaries-date-fixed/`、`../2026-10-13-tool-evidence-boundaries-date-final/`，未覆盖失败记录。软日期第一次评估将 commit_batch 交给修复校验器，日志错误显示 stale workflow repair；根本失败是没有提出要求的修复动作。

## 测试与核对

TDD先验证了字段/继承、固定冲突与等待恢复、模型软日期修改、工具不顺延、非法修复反馈和新日期定向查询。追加用例分别证实“相同硬日期不能被修复补丁降级”“新的出发日不能越过硬抵达日期”“日期跨度不能改变硬住宿晚数”“已有方案修改入口不能软化继承的全局期限”。均先观察失败，再补最小实现并观察通过。

## 适用边界

这次真实模型检查是小样本的单轮选择回放，不是首次自然语言强度提取或新日期供应商端到端测量。强度提取依赖主模型正确理解用户原文；程序负责已提取字段的校验和继承保护。政策适用性重新解析沿用现有程序流程。

到达查询可能提前过滤迟到车次，空列表无法证明固定日期客观不可行，因此不会自动按“全候选迟到”追问。未知信息继续作为具体缺口反馈。任意复杂跨段冲突仍依赖模型理解和既有全程校验，本次没有新增通用约束求解器。

工具清洗和未来信息获取 Agent 均未在本次启用。提示词约束不是全面撤销合法查询接口，既有调用预算、无进展限制和报价能力守卫仍保留。
