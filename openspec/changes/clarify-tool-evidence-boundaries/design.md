## Context

用户明确要求修改提示词，不继续调整数据清洗。select_batch 当前包含“缺必要资料时才补查询”，batch_query_contract_prompt 包含“报价被过滤且授权时必须刷新”；finalize 允许 needs_requery，step 也包含按需 dispatch 与 repair_tasks。仅追加一句停止规则会留下相互矛盾的指令。

当前程序已支持 commit_batch.allow_repair=false：保存有依据的草稿，校验后直接结束；有阻塞问题返回 partial，无阻塞问题仍可 completed。酒店地点能力缺报价还存在程序兜底停止。用户随后要求把工具层的日期顺延改为模型综合调整，并区分强制条件。因此本次范围扩展到字段契约、日期修复与冲突分流，不再是仅改提示词。

## Goals / Non-Goals

目标：统一各主 Agent 提示入口，让接口能力缺口直接收尾；由模型合理调整允许变动的去程、返程与住宿日期，明确硬条件冲突并等待用户反馈。

非目标：不改工具数据清洗、候选裁剪和供应商；不把有界候选视图改成原始 API 全量数据。上下文投影仅需透传新增条件字段。保留首次查询、独立任务、用户后续明确查询和新日期所需定向查询；不新增 Agent、业务状态或交通方式。

“使用全部返回结果”的实现解释是综合当前上下文中各任务实际返回的事实，不自行假设还存在可获得的房价、库存或距离；不宣称当前候选列表已覆盖全市场，也不把分页标记解释成接口能力不足。

## Decisions

1. 先选择已有候选、保留固定硬条件和政策；能在已有证据中重组就重组。接口不提供字段或请求失败时直接说明，不用日期调整或反复刷新掩盖缺证据。候选真实不满足时间衔接且相关日期为软条件时，允许模型提出新的整体日期安排。
2. 批量提交显式使用 allow_repair=false，缺选择用 null；unverified_requirements 写清查不到的字段或无法满足的条件。非阻塞缺口也可以写入，但最终完成状态仍由现有校验决定。
3. 新增 condition_strengths，值仅 hard/soft，与 field_sources 分离。新提案在 workflow 条件和 task 条件对应层级标记；task 继承全局硬边界，不能降级。无软化依据的明确日期按 hard，用户明确“尽量/最好/可调整”按 soft，系统建议按 soft。本次仅日期字段及 nights 使用该强度规则；预算、人数、路线及政策保持现有保护。旧记录无字段时 user/context 或已确认全局条件按 hard，proposal/default/derived 按 soft，但从全局硬边界推导的条件仍继承硬约束。
4. 移除 train_search 成功空结果时自动尝试 +1/+2 天的工具规则。扩展 repair_tasks 支持 task_updates=[{task_id, conditions}]，conditions 仅本次可调整的日期和 nights；程序核对版本、实际相关问题、软条件、全局硬边界及政策适用性，再失效相关证据并处理依赖。去程和返程各是 task 的 departure_date，不增加重复 return_date。
5. 用户已确认新日期允许定向查询：缓存有该日期有效证据时复用，否则只查受影响的火车和酒店；旧报价不可改日期冒充新报价。模型不能保证新日期有票，失败时反馈本次缺口，不靠不停改变日期逃避停止规则，沿用已有调用和无进展限制。
6. 完整校验后，有证据证明硬日期条件冲突、且无法通过已有候选重组或允许的软日期调整解决时，程序保存明确冲突问题并返回 user_input_required，等待用户决定。缺候选、接口失败、未知抵达或无报价仅是证据不足，不能自动当成“硬条件必然不可兼容”。已有可行候选仍应先改选，不因模型选错一班车立刻询问用户。模型标记强度不能替代对原文的正确理解；提示、来源与迁移规则共同保护，不宣称程序能独立理解所有自然语言。
7. 删除批量提示中的无条件刷新样例和超标必须刷新指令；保留工具能力、参数合法性及每晚金额语义。明确“缺字段停止”与“调整软日期后验证新参数”的差别。
8. step 保留未查询任务的首次 dispatch；finalize 不输出缺口驱动的 needs_requery；已有修改入口透传强度与合法用户授权，未受影响组件继续复用。硬条件仅能由用户明确修改，政策要求不得经条件软化绕过。
9. 新增实际字段、修复和程序分流测试并执行 TDD；不新增逐字断言提示词或根据提示词硬编码结果的假模型测试。真实模型效果用少量已保存上下文回放评估，供应商不联网。

## Risks / Trade-offs

提示词是模型行为引导，程序仍接受合法查询动作；若模型违背指令，现有预算、无进展与能力守卫仍是最后保护，不承诺从程序层杜绝查询。真实回放属于小样本检查，不保证所有请求都服从。

同轮不主动刷新缺口可能错过后续报价，这是用户本阶段要求的取舍。模型提出日期变化时额外查询有实际新参数依据，应独立计入成本。不能将查不到说成酒店不存在或政策允许，不能通过软化硬边界让结果变成 completed。

## Technical Review

已核对主入口、批量提交、停止标记、字段来源、工具日期回退、修复接口及已有日志。新字段需要同时修改契约、持久化投影、守卫、修复和更新入口，不能仅改提示词；强度优先级与旧记录处理必须一致。未来信息获取 Agent 保持延期。用户已确认新日期定向查询，并通过“也做”确认强度字段和冲突规则，进入单代理、当前目录实施。
