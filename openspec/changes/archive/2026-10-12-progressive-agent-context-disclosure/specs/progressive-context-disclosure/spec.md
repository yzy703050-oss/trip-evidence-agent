## Purpose

保留差旅系统现有 JSON 状态机、候选分页与缓存执行形式，针对主模型判断阶段精简暴露内容，减少无关字段和重复数据，同时保留选择引用、关键事实、数据缺口和来源可信性，完整存储继续用于程序校验。

## ADDED Requirements

### Requirement: 按领域和判断目标精简候选

系统 SHALL 按火车、酒店报价、酒店地点分别投影，默认保留引用、时刻、站点、价格、名称、必要位置和可用性等判断事实，MUST NOT 默认展开 URL、原始来源、坐标和证据原文。模拟、过期、未核实及关键缺口 SHALL 保留。筛选排序和一页候选 SHALL 沿用；完整存储 MUST NOT 因投影被修改。

#### Scenario: 火车选择
- **WHEN** 主模型比较火车候选
- **THEN** 收到价格、时刻、站点和候选 ID，来源 URL 不进入请求，未知到达日期仍明确

#### Scenario: 酒店仅提供地点
- **WHEN** 查询仅有酒店地点，没有报价或库存
- **THEN** 保留地点类型及未核实状态，不将其表现成可订房源；评分等字段仅在有关条件需要时提供

### Requirement: 主视图去重并精简双向委派

系统 SHALL 默认提供轻量任务索引和唯一详细当前任务；当前候选只在必要结果字段出现一次，子结果保留摘要与查询元数据。系统 MUST NOT 给子 Agent 传入全部 workflow、其他任务、主历史或主读取消息。每次子调用 SHALL 独立，主历史仍只按完整旧用户轮次压缩。

#### Scenario: 当前段有大量查询
- **WHEN** 程序向主模型及子 Agent 组装当前任务上下文
- **THEN** 无关旧草稿与候选不被重复展开，当前有效引用和必要衔接事实保留

### Requirement: 保留现有 JSON 状态机和分页协议

系统 SHALL 继续通过 dispatch、draft_task、validate_workflow、finish 及受控修复 JSON 执行业务。系统 MUST NOT 为字段精简新增主 Agent 原生只读工具循环或强制列表后再次读取单项详情。现有 candidate_offset 与有效缓存 SHALL 可继续使用，最终回复 SHALL 基于 reply_facts。

#### Scenario: 一页候选足以决定
- **WHEN** 必要字段已经足以选择方案
- **THEN** 主模型直接输出合法草稿动作，不强制增加详情读取模型请求

### Requirement: 外部失败与来源边界保持

系统 SHALL 保留现有失败/模拟返回，不新增供应商失败排查、自动补查或模拟策略改造。模拟结果 MUST NOT 冒充真实接口成功。

#### Scenario: 现有模拟路径
- **WHEN** 子结果使用模拟候选
- **THEN** 主视图保留简短模拟标记，存储保留完整来源，不额外请求供应商排查
