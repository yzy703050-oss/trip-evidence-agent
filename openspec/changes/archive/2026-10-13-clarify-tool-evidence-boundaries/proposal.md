## Why

主 Agent 提示词仍把工具结果缺失、候选超标等问题引向补查或刷新，导致已识别接口能力边界后继续查询。用户要求现阶段以已返回事实完成可完成部分，查不到或无法满足的要求直接说明，本轮不为补齐缺口再查。

## What Changes

- 修改主 Agent 批量选择、兼容工作流、最终汇总和已有方案修改中的相关提示，删除同轮缺口自动补查、超标强制刷新等冲突指令。
- 缺资料或无法满足硬条件时保留已有选择，记录明确缺口；批量提交使用 allow_repair=false，程序仍按现有规则校验并结束本轮。
- 区分“本次未查到/无法核实”与“客观不存在”；软偏好未核实不等于硬政策已满足，也不自动把可完成方案判为失败。
- 首次必要查询、后续用户明确发起的新查询或刷新，以及明确修改后的既有执行机制保留。
- 新增 condition_strengths 区分 hard/soft，与条件来源分离；旧记录缺少标记时保守保护用户已固定条件，政策硬约束不能降级。
- 移除工具层默认日期无候选时顺延一天、两天的自动策略；改由主 Agent 在硬条件内综合提出去程、住宿和返程日期调整，程序校验并处理依赖。
- 明确固定硬条件冲突的用户反馈与等待机制；证据不足和可调整的软条件不自动进入等待分支。
- 本次不修改工具返回数据或清洗投影、不增加状态或 Agent；保留政策强制校验。用户已确认模型调整日期后允许定向查询新日期，不能复用旧日期的报价、余票或房价。

## Capabilities

### New Capabilities

- `travel-condition-strengths`：条件强度、受控模型日期调整及硬条件冲突反馈。

### Modified Capabilities

- `consolidated-travel-execution`：主 Agent 在工具结果返回后停止缺口驱动的自动重查，使用现有提交与收尾接口披露限制。

## Impact

涉及主 Agent 提示、提案/修复契约、条件保护、查询参数与依赖处理、工具日期回退和持久化兼容。查询清洗和供应商不变；repair_tasks 需要受控日期补丁，状态与 Agent 数量不增加。强度字段本次先用于日期及住宿晚数，不放宽现有金额、人数、路线或强制政策规则。停止补查仍主要通过提示引导，日期越权与明确硬条件冲突由程序约束。
